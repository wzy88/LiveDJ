# DJ 口播稿生成知识库

## 目标

Claudio 的口播不是推荐理由文案，也不是报幕。目标是把一组歌编成一段正在发生的私人电台节目，让用户觉得歌单有流动、有陪伴、有现场感。

核心公式：

`用户当下场景 + 歌单编排 + 歌曲听感 + 可用外部素材 + 播放时机 = DJ 口播`

## 调研依据

- Live365 的广播脚本指南强调，音乐电台脚本的重点之一是让歌曲、新闻、体育、广告等元素之间形成自然 transition；音乐脚本应比谈话节目更松，常用 talking points，而不是每段都写满对白。
- Radio))) ILOVEIT 的 jock talk 文章强调，音乐台的口播不能让用户觉得是打断音乐；人格连接很重要，但必须保护节目向前的动势。
- 广播主持研究资料把主持分成播音式、策划式、核心式。我们要的是策划式/核心式 DJ：理解节目内容，把编辑意图和歌曲内容融会贯通，而不是流水线报幕。
- 中文主持词写作资料里有一个可迁移原则：主持词是“引个话、串个词”，篇幅应短小、平实、服务议程。音乐口播同理，不能喧宾夺主。
- 晚安/早安电台样稿显示，优质稿子的核心不是反复点题，而是先建立时间场、身体感和心理入口，再轻轻给一个陪伴动作。知乎相关页面当前抓取受限，正文 403；搜索摘要能看到的方向是“像朋友一样交流、制造场境效应”，但不能把不可见正文当成一手依据。

## 早安/晚安电台样稿观察

### 常见结构

优质或接近优质的早晚安电台稿，通常不是直接讲“你今天很累/你正在失眠/你要努力”，而是按这个顺序走：

1. 时间场
   - 早安：晨光、窗帘、风、鸟声、新的一天。
   - 晚安：夜色、城市安静、灯、风、被窝、一天收尾。
2. 轻问候
   - 不用长篇问候，通常一句就够。
   - 问候的作用是建立“我在这里”，不是介绍主播身份。
3. 一个可感知的小动作或画面
   - 关掉屏幕、放下白天、把窗帘拉开、给烦恼一个期限、让心慢下来。
4. 一个温柔判断
   - 不是大道理，而是把用户可能的状态说轻一点。
5. 收到一个可执行的陪伴动作
   - “剩下的时间还给自己”
   - “先把今天放下”
   - “让新的一天慢慢开始”

### 好的地方

- 有时间气味：不是抽象说“治愈”，而是让用户知道现在是清晨或夜里。
- 有身体动作：醒来、闭眼、放下、呼吸、走出门、关灯。
- 有低压陪伴：不催用户立刻积极，也不替用户总结人生。
- 有“轻触即走”的情绪：只点一下，不把情绪讲死。
- 有节目感：用“今晚/清晨/这一刻”把内容放进一个小场域。

### 不好的地方

网上很多范文也有明显问题，不能照抄：

- 主持腔重：开头就“欢迎收听某某电台，我是主播某某”。
- 鸡汤套话多：每天、新开始、梦想、坚持、你最棒，信息密度低。
- 情绪过满：动不动爱、错过、人生、泪流满面，容易压住音乐。
- 主题复读：早安每句都早安，晚安每句都晚安。
- 不服务歌曲：适合纯读文，不适合音乐歌单串联。

### 可迁移到 Claudio 的原则

1. 用户说的场景只出现一次，后面转成画面、动作和声音。
   - “加班”转成：灯还亮着、桌面、消息、屏幕、肩膀、夜色。
   - “骑车”转成：风、踏频、路口、呼吸、手扶稳、下一个坡。
2. 口播不要一直解释用户为什么需要这首歌。
   - 解释一次即可，后面让声音和动作自己成立。
3. 每段必须短。
   - 早晚安电台可以长，因为它是读文；音乐 DJ 口播要更短，不然打断歌曲。
4. 一段只做一个动作。
   - 叫醒、放松、推进、换气、收住，不要一句里塞完全部。
5. 允许留白。
   - 好的电台稿不是每秒都有意义，而是给音乐留位置。

### 多平台样稿补充观察

- 范文类早安电台稿常用“清晨、阳光、窗帘、晨风、咖啡、吐司”等具体物象建立早晨，但也高频落入“梦想、坚持、你最棒”的正能量套话。可学物象，不学口号。
- 豆瓣哄睡/深夜电台文本常用长段独白、人生感慨、关系困境和“你不孤单”式陪伴，适合纯语音节目，不适合直接压在音乐上。可学“夜色、孤单、故事感”，但要压短。
- Apple 播客上的治愈电台多以 6-8 分钟单集承载完整情感主题，标题直接指向关系、扛事、幸福、爱。这说明情感电台有明确主题线，但 Claudio 的一首歌口播不能写成完整情感文章。
- Spotify/Firstory 的睡前晚安电台常用“睡前故事”“晚安”“每晚固定相见”等仪式感。Claudio 可借“固定陪伴感”，但不能每段自我介绍或反复说晚安。
- 荔枝上的治愈/甜蜜节目文案常有高密度情绪词和恋爱表达，氛围感强，但容易过甜、过满。Claudio 要保留温度，降低糖分。

结论：早安/晚安电台给我们的不是句子模板，而是“场域方法”：

`时间场 -> 小动作 -> 轻判断 -> 留给音乐`

音乐口播每段只取其中一个动作，不能把完整晚安稿的情绪密度搬进歌曲中间。

### 样稿转化规则

不要写：

```text
你现在正在加班，所以这首歌适合陪你加班，让你在加班时不那么疲惫。
```

改写方向：

```text
灯还亮着，就先别跟今晚较劲。让这段声音在旁边铺开，手上的事一件一件来。
```

不要写：

```text
这首歌节奏感强，可以让你骑车的时候更有动力。
```

改写方向：

```text
风从耳边过去的时候，先别急着冲。让脚下的圈数稳下来，速度会自己回来。
```

不要写：

```text
早安，新的一天开始了，希望你努力追求梦想。
```

改写方向：

```text
窗帘外面已经亮了。先不用马上进入满格状态，给自己几分钟，把今天慢慢打开。
```

## 当前运行时结构

运行时以六首歌为一个节目段，不再默认给每首歌安排完整口播：

1. `block_open`：第一首开头建立用户当下的场景。
2. `presence_touch`：第二首结尾用一句短话表示“我还在”。
3. `callback`：第三首开头承认时间经过，并呼应前文。
4. `trust_window`：第四首完整留给音乐，`stages: []`。
5. `mid_anchor`：第五首开头根据节目进程调整能量或情绪方向。
6. `soft_handoff`：第六首开头短触碰，结尾说明陪伴仍会继续。

六首歌合计 6 个口播片段，阶段数量为 `[1, 1, 1, 0, 1, 2]`。`opening`、`bridges`、`nextTease` 和 `closing` 仍是兼容的文稿字段，但是否播出、何时播出由节目钟决定。

## 生成流程

### 1. 先把用户输入转成状态，而不是关键词

用户说“我现在在加班，播点音乐”，不要把“加班”当成每段必须出现的词。

应转成：

- 时间感：夜里/工作后段/桌前
- 身体状态：累、分神、需要续航
- 心理诉求：不想被打鸡血，不想被提醒痛苦，只想有音乐陪着把事情做完
- 禁忌：反复说“加班”、反复劝努力、反复提任务

场景词进入底层，不挂在嘴上。

### 2. 歌单要先形成节目线

五首歌不能只是五个匹配结果。应先分配节目角色：

- 入场：降低摩擦，让用户进入播放状态
- 稳定：给身体/注意力一个持续节奏
- 转场：换一种颜色，避免单调
- 推进：在中后段给一点动势
- 收束：不继续拔高，让人从场景里出来

每首的口播只服务自己的角色，不把同一句“适合加班/适合提神/适合办公”换歌名复读。

### 3. 口播不是歌曲介绍

播放器已经显示歌名和歌手。口播不需要承担报幕职责。

可用歌名/歌手的场合：

- `nextTease` 需要明确下一首时。
- 使用热评、歌手资料、新闻素材时，必须锚定具体歌曲以免听众困惑。
- 用户点名歌曲或歌手时。

不应使用的方式：

- “接下来为你播放……”
- “《X》和 Y 放在这里……”
- “这首歌由 Y 唱出来……”
- 每段开头都用歌名/歌手做主语。

### 4. 外部素材只在能增加现场感时使用

天气、新闻、八卦、热评、城市信息不是为了凑丰富度。

合格使用：

- 天气变成身体感：风、湿度、热、冷、路感、窗外光线。
- 新闻变成背景气味：城市今天在发生什么，但不抢歌。
- 八卦变成轻松陪伴：只适合用户要娱乐、解闷、闲聊时。
- 热评变成听众共鸣：少量引用或转述，不能连续复读。

不合格使用：

- 每段都硬塞“今天新闻/天气/八卦”。
- 用素材替代节目判断。
- 编造没有输入的事实。

### 5. 每个节目钟角色要有独立任务

- `block_open` 只负责“看见听众”，从状态、动作、环境或时间进入。
- `presence_touch` 只保留一句短触碰，不解释歌曲，不要求听众回应。
- `callback` 必须承认时间经过，或呼应前面说过的动作和状态。
- `trust_window` 不生成、不显示、不播放口播。
- `mid_anchor` 必须做一次可感知的调整，不能只是换一种说法继续推荐。
- `soft_handoff` 不做节目结束式告别，只说明后面的声音还会继续。

## 质量门槛

一段口播合格前必须通过：

1. 是否让歌单更活，而不是只解释推荐理由？
2. 是否保护听歌心情，而不是反复提醒用户处境？
3. 是否服务当前播放时机？
4. 是否有信息增量？
5. 是否听起来像真人 DJ，而不是后台算法？
6. 是否避免用歌名/歌手当拐杖？
7. 是否没有硬塞外部素材？
8. 是否适合配在音乐上，不喧宾夺主？

- 场景词进入底层，不要每段复读用户关键词。

## 当前代码状态

- `server/track-research.js` 是可插拔检索层。配置 `TRACK_RESEARCH_API_URL` 时优先调用资料模型/搜索服务；未配置时会走受限的公开搜索兜底。搜索结果必须通过歌名、歌手、音乐语境和来源质量门控，宁可为空，也不能把旅游攻略、歌词镜像、下载页等脏素材喂给口播。
- `server/talk-brief.js` 已引入 `talkStrategy`。纯场景请求走 `scene_first`，不强制 opening 点出歌名歌手；有热评、歌手资料、城市资讯或检索资料时走素材锚定。
- `server/llm.js` 的 prompt 已接收 `contentPack.research` 和 `talkBrief.materials.songResearch`。后处理会让 `scene_first` 保持不报幕，但仍允许桥段使用当前歌曲材料。
- `server/program-clock.js` 负责六首节目钟和最终 stages。前端明确把 `stages: []` 当成音乐留白，只有旧数据没有 stages 属性时才使用 fallback。
- 推荐图支持 `data/song-graph.json` 和 `data/song-graph.json.gz` 两种形态，避免本地只有压缩图时节目构建失败。

## 检索增强层

`trackResearch` 的职责不是把百科资料塞进口播，而是把公开搜索/资料模型结果整理成 DJ 能用的少量素材。

输入建议：

```json
{
  "query": "歌曲名 歌手 歌曲 资料 听感 评论 用户场景",
  "track": {
    "title": "一半一半",
    "artist": "Top Barry / INDEcompany",
    "genres": ["R&B", "流行"],
    "moods": ["松弛"],
    "scenes": ["工作学习"]
  }
}
```

搜索服务返回建议：

```json
{
  "items": [
    {
      "title": "公开资料标题",
      "snippet": "这首歌带有 R&B 低频和贴近耳边的人声，节奏不急。",
      "url": "https://..."
    }
  ]
}
```

进入口播模型前会被压成：

```json
{
  "audibleCues": ["R&B低频", "人声贴近", "节奏不急"],
  "listenerAngles": ["桌前工作时不抢注意力"],
  "backgroundFacts": ["公开讨论里常把它放在夜里独处语境里"],
  "talkSeeds": ["低频和人声可以放近一点，适合在旁边铺开"]
}
```

质量原则：

- 检索资料只能增加“听感、场景、评论共识、背景事实”，不能变成歌曲百科。
- 只保留 3-5 个可用于口播的点。
- 过滤下载、铃声、网盘、歌词搬运、无损 MP3 等噪音。
- 没有可信资料时宁可为空，不要编。

## 下一步改造方向

1. 接入真实搜索/资料模型服务到 `TRACK_RESEARCH_API_URL`，用线上样本持续调清洗规则。
2. 生成前进一步建立 `programLine`，让每首歌角色和 `trackResearch.talkSeeds` 对齐。
3. 测试输出必须按 `stages` 展示完整口播，不再用五段概念稿评估。
4. 增加更多固定场景回归测试，例如早安、晚安、骑车、通勤、做饭、运动。
